# AI 终端启动器 — 已知缺口与后续

本文是**现状与缺口**，不替代 [04-使用说明.md](04-使用说明.md)。待办未做不等于已经解决。

## 当前结论

- 日常启动 CLI 与互拷已在本机使用：窗口网格、配置刷新、`.command` 启 Terminal、rsync/scp、连接串解析、免密联想、远端逐层浏览、本机中转。
- 源码分两层：`src/Core.swift`（纯逻辑，Foundation only）+ UI 层（AppKit，按职责拆成 `main.swift` 入口 / `AppShell.swift` 辅助 / `AppDelegate.swift` 窗口与菜单 / `CopyForm.swift` 表单 / `CopyRunner.swift` 执行 / `SuggestionController.swift` 候选框，布局见 [03-架构设计.md](03-架构设计.md)）。
- Core 有全量命令行断言（`./scripts/test.sh`，无 GUI 副作用，条数见 [05-测试与验收.md](05-测试与验收.md)），并有 GitHub Actions CI；`--selftest` 仅做 GUI 冒烟（加 `--no-launch` 不会点按钮、不弹 Terminal）。
- 安装产物 `~/Applications/AI终端启动器.app`；真实配置仍是 `~/.config/ai-launcher/config.json`。
- 跨机链路 2026-11-03 已在两台真实内网机上验过（推送 / 拉取 / 中断续传 / 断网强杀 / 直拷 / 两种中转 / 中文路径 / 改名幂等），数据见 [05-测试与验收.md](05-测试与验收.md)。此前只在单容器 Docker 里验过，本轮无代码改动。
- 周报 2026-10-25 已记录互拷与约 25 台免密主机。主机清单只在 `~/.ssh/config`，不进本仓；`config.json` 的 `copy.hosts` 已废弃（0.5.0 起忽略，旧的「预设」下拉没了，联想覆盖同一批机器）。

| G-23 | ~~「解析」人工测试没填入；GUI 自测假绿~~ **已解决** | 0.5.0 把回填押在「用户点过路径框」上，而自测是手工塞 `lastPathField` 再直接调 `parseConn`——绕开真人操作，日志 PASS、真机 FAIL。按 TDD 重做：先写 4 条模拟真人操作的 GUI 用例（只走 `firstResponder` 切换 + 按钮 `performClick`，不设状态变量、不直接调被测方法），跑出 0/4 红灯；诊断出 `--selftest` 里窗口非 key、`textDidBeginEditing` 一次都不发，真机上路径是 `last-copy.json` 回填时同样没有焦点记录。修法：把「填哪个框」抽成纯函数 `resolveParseTarget`（焦点优先、无焦点按框内内容兜底，两框都空给源一个起点），补 7 条单测；焦点记录加通知观察双保险；状态栏写明填了哪个框、怎么换。最终 381 条单测 + 6/6 GUI 冒烟全绿 | 往后一律「先写能复现真机操作的失败用例 → 看红灯 → 再改生产代码 → 看绿灯」；禁止在自测里直接调被测方法或手工设置被测状态 |

| G-24 | ~~界面摆着几个「看得见却没接线」的控件，自测只查「存在」~~ **已解决** | 审查发现五处：①密码框从不进命令，只在解析回填 / 表单快照 / 自测存在性断言里出现；②「递归」复选框被 `-a` 吞掉（勾「保留属性」时取消它照样递归，实证 `rsync -r -a` vs `rsync -a`）；③凭据三框可编辑，但改 IP 不影响命令（命令用的是路径框里的 `user@host`）；④连接串不点「解析」就完全不进命令；⑤tar 流中转忽略全部选项且状态栏只说了一半。修法：删密码框与「递归」复选框、`CopyParams`/`CopyMemory` 去掉 `recursive`（命令恒带 `-r`、旧 JSON 键忽略）、凭据行改只读并标注、未解析连接串明确拦下、tar 流状态栏一次说全。**方法论**：新增 `scripts/check-ui-wiring.sh`（每个输入控件必须有值被生产路径读取的证据，自带假控件自检防检查器假绿），接入 `test.sh`/CI；删掉 10 条「控件存在」假绿断言，换成 5 条真人操作接线契约；`check-docs.sh` 加第 5 项拦「文档还在写已下线功能」；docs/05 建「控件 → 消费点」映射表 | 静态检查只能抓「值没人读」，抓不到「读了却没用」；后者靠 Core 单测断言「选项改变时命令是否真的改变」覆盖（0.5.2 的固定递归三条就是例子） |

### 2026-11-11（状态栏按事实说话，无新机制）

| 项 | 处理 |
|----|------|
| 起因 | 沙箱里拉起 app 时 `open xxx.command` 什么都不做，状态栏却照样显示「已运行 12s」——它给的是一个字节都没传的假像。追下去发现这不是测试环境的小毛病，而是状态来源本身错了 |
| 根因 | `.command` 交给 Terminal 是**单向通道**：`/usr/bin/open` 对「文稿被拦」返回 0，`NSWorkspace.open(_:withApplicationAt:configuration:completionHandler:)` 也只回报 `error=nil` / `bundle=com.apple.Terminal`（两者都实测过，脚本确实没执行）。换接口解决不了，因为没有接口知道 |
| 修法 | 不新增任何定时判定，改为**只陈述已知事实**：脚本第一条动作就是写 `[时间] 开始 …`，读到它才算「运行中 Ns」；没读到就说「已交给 Terminal，等待脚本开始」。`CopyOutcome` 增加 `started`，`parseCopyLogOutcome` 只认行首为 `[` 的标记（rsync 自己的 `[14720]` 行不会误判） |
| 顺带 | `launchCommandInTerminal` 改为返回 `Bool`（`open` 的退出码在「文件缺失 / 没有程序能打开它」这类错误上仍然可信），失败时状态栏直接给出可手动执行的脚本路径 |
| 怎么验的 | 三种状态都用真实脚本产物跑过：脚本未执行 → 「已交给 Terminal，等待脚本开始」（日志目录确实不存在）；注入延迟让拷贝停在中途 → 「运行中 12s」（日志里只有开始行）；正常跑完 → 「✅ 拷贝完成（退出码 0）」 |
